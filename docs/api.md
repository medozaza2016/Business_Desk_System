# HTTP API

Base URL: `https://desk.luxoritpro.com`. All responses are JSON except the print sheet (HTML) and the
CSV export. Every protected route requires the `q_session` cookie set by `POST /api/setup` or
`POST /api/auth/login`.

Errors always look like `{ "error": "machine_readable_code" }` with a matching HTTP status.

## Authentication model

- One **shared passcode** per deployment, stored as PBKDF2-SHA256 (`100,000` iterations, per-record salt)
  in the `settings` table under the key `auth_passcode`.
- The session cookie is signed with HMAC-SHA256 using a key derived from the stored passcode hash:
  `hmac_key = "q_session.v1:" + hash`. Rotating the passcode therefore invalidates every existing cookie.
- Cookie format: `q_session=v1.<base64url(payload)>.<base64url(hmac)>`, `HttpOnly`, `Path=/`,
  `SameSite=Lax`, `Secure` on https, `Max-Age` from `SESSION_HOURS` (default 12).
- Payload: `{ "n": "<display name>", "exp": <unix seconds> }`. No database read is required to
  authenticate — only the single `settings` row, which is fetched per request.
- Failed logins are throttled in-isolate: 8 attempts per IP per 10 minutes (`429 too_many_attempts`).

### Public routes

| Method | Path | Body | Returns |
|---|---|---|---|
| `GET` | `/api/health` | – | `{ok, service, version}` |
| `GET` | `/api/auth/status` | – | `{setup, signed_in, name, session_hours}` |
| `POST` | `/api/setup` | `{passcode, name?}` | First run only: creates the passcode, seeds a starter company + template v1, signs in. `409 already_configured` afterwards |
| `POST` | `/api/auth/login` | `{passcode, name?}` | `{signed_in, name}` + cookie. `401 invalid_passcode`, `429 too_many_attempts` |
| `POST` | `/api/auth/logout` | – | `{signed_in:false}`, clears the cookie |
| `GET` | `/api/companies/:id/logo` | – | Raw logo bytes with their stored `content-type`; `404 logo_not_found` when the company has none. Public because the print previews run in sandboxed iframes (see below) |

Passcode rules: 6–200 characters. `name` (optional, ≤60 chars) only tags the audit trail
(`audit_events.actor`) and the header chip. The desk UI does not ask for it, so browser sessions are
recorded as `Shared user`; send it from scripts or curl when you want attribution.

### Deleted records, permanent deletion and audit history

Quotation cancellation is a soft delete. The quotation remains in D1 with `deleted_at` set and appears in the quotation ledger's **Deleted** view. A deleted quotation can be restored, or permanently removed only after typing its exact quotation number. The Worker rejects permanent quotation deletion unless the record is already soft-deleted.

Agreements follow the same rules on their own tables: `DELETE /api/agreements/:id` sets `deleted_at`, the record moves to the agreements ledger's **Cancelled** view, `POST …/restore` brings it back and `DELETE …/permanent` requires `confirm_number` (`409 agreement_must_be_deleted_first` when the record is still active, `409 agreement_confirmation_required` when the typed number does not match).

Company deactivation is separate from permanent deletion. Permanent company deletion requires typing the exact company name and removes that company's quotations and agreements (including soft-deleted rows), signed-scan records and R2 objects, templates, numbering sequences, company row and company-owned R2 files. Global settings and audit events are not deleted.

Permanent deletion writes its audit event in the same D1 batch as the corresponding data removal. R2 cleanup follows the D1 batch; the response reports any failed R2 deletes so they are not silently treated as successful. Audit events can be read through `GET /api/audit` and are paginated with `limit` and `offset`.

### Public share links

`GET /s/<token>` is the customer-facing page for one quotation: the figures, the amount in words and the
signed page. It carries no session and no API call — one HTML document plus one image (or one PDF). The
only script is the Print button, allowed through a `sha256` CSP hash.

| Method | Path | Returns |
|---|---|---|
| `GET` | `/s/<token>` | HTML page (`404` + a branded "link no longer active" page for an unknown, revoked or cancelled token) |
| `GET` | `/s/<token>/scan` | The signed page (image or PDF); `?download=1` returns it as an attachment |

- The token is 24 random bytes (base64url, 32 chars) minted with the first signed copy and stored in
  `quotations.share_token`; the raw value never appears in an `/api/` payload (only `share_path`).
- Responses carry `x-robots-tag: noindex, nofollow, noarchive`, `referrer-policy: no-referrer` and
  `content-security-policy: default-src 'none'; img-src 'self' data:; style-src 'unsafe-inline'; script-src 'sha256-…'; …`.
- *Print* has two shapes, because paper does not come out of an HTML page for free:
  - a picture signed copy prints the page itself — `window.print()` plus `@media print` styles that drop every
    control and start the signed copy on its own A4 sheet;
  - a PDF signed copy gets a **link** instead of the script (`Print the PDF` → `/s/<token>/scan`), because
    `window.print()` would print the figures and leave the signed page behind. The file opens in the
    browser's viewer, which prints the real document — page count, size and all.
- `og:` tags are emitted for the quotation number, the vehicle and the scan, so a WhatsApp preview shows
  the paperwork bubble rather than a bare URL. A PDF signed copy has no `og:image` (a PDF is not an image);
  the page shows it as a document tile with its size and a tap-through link.

Agreements get their own namespace, so a `/a/` URL can never be mistaken for a quotation:

| Method | Path | Returns |
|---|---|---|
| `GET` | `/a/<token>` | The customer page for one agreement: kind (sale or purchase), vehicle, both parties, the money with the balance, and the signed page. `404` + a branded page for an unknown, revoked or cancelled token |
| `GET` | `/a/<token>/scan` | The signed page (image or PDF); `?download=1` returns it as an attachment |

The rules are the ones above: the token is 24 random bytes stored in `agreements.share_token`, it is minted
with the first signed copy, rotation invalidates every pasted link, revoking removes it, and the page needs
neither a session nor a cookie. Print behaves the same way (the page prints itself for a picture, the button
links to the file for a PDF).


### Company logo

The logo is stored in R2 (`ASSETS` binding, key `logos/<companyId>-<random>.<ext>`) and the company row
only keeps `logo_key`; `logo_url` in company payloads is the ready-to-use path.

- Accepted formats: **PNG, JPEG, WebP**. The Worker checks the file signature as well as the declared
  type, so a mislabelled or renamed file is rejected (`415 unsupported_image_type`).
- Maximum size **512 KB** (`413 logo_too_large`). SVG is deliberately refused — it is a document, not a
  raster image, and would be served from the same origin as the desk.
- Uploading a new logo deletes the previous object. `GET` is the one **public** route: the print previews
  render inside `sandbox`ed iframes whose opaque origin would drop the `SameSite=Lax` cookie, so a guarded
  read would simply 401 and print a broken image. Only the image bytes are exposed (the company UUID is
  unguessable, uploads and deletes stay authenticated), and the response carries
  `x-content-type-options: nosniff`, `content-disposition: inline` and
  `content-security-policy: default-src 'none'; sandbox`.
- `template_uses_logo` is `false` when the live template never asks for `{{logo_url}}`, i.e. the file is
  stored but cannot appear on the sheet until the template is updated (see
  [`template-placeholders.md`](template-placeholders.md#company-logo-and-watermark)).
- The printed sheet resolves the logo from the **live company profile** (like the letterhead), so a
  replaced or removed logo can never leave a broken image on a reprint.

```bash
curl -s -b jar.txt -F "file=@logo.png;type=image/png" "$BASE/api/companies/$CID/logo"
curl -s -b jar.txt -o logo.png "$BASE/api/companies/$CID/logo?v=whatever"
curl -s -b jar.txt -X DELETE "$BASE/api/companies/$CID/logo"
```

Quotation fields: `model` ≤120, `year` ≤20, `chassis` ≤120, `comments` ≤300 (optional, may be cleared
with `""`; newlines and repeated spaces collapse to one line), `amount` 0–99,999,999.99 (commas and
decimals accepted), `quote_date` in `YYYY-MM-DD` (calendar-validated).

Numbering: `quotation_prefix + YYYY + "-" + 5-digit serial`, allocated atomically by the Worker per
company and year through `quote_sequences`. The new-quotation form displays a read-only preview
(`auto · <number>`) and never accepts a manual number. The create API always allocates the next free
serial server-side, even when a caller includes a `quote_number` field in the request.

### Signed copies (scans)

- One page per quotation: `quotation_scans` is keyed by `quotation_id`, so a re-scan replaces the stored
  copy. Bytes live in R2 under `scans/<companyId>/<quotationId>-<random>.<ext>`; the row keeps only
  `r2_key` plus `bytes`, `width`, `height`, `content_type` and `source`.
- Accepted formats: **PNG, JPEG, WebP** (`≤ 4 MB`) and **PDF** (`≤ 12 MB`) — a signed page often arrives
  from a desktop scanner as a PDF. The signature is checked in every case, so a renamed file is rejected
  (`415 unsupported_scan_type`, `accepted` lists the four types) and an oversized one gets
  `413 scan_too_large` with the ceiling that applied.
- Three ways in, all landing on the same route: the in-app scanner (`source=scan`), a photo from the
  gallery (`source=upload`, corrected in the browser by the same pipeline) and a PDF (`source=upload`,
  stored byte for byte). `width`/`height` are only meaningful for a picture; a PDF stores `0`.
- The desk's scanner (`public/scan.js`) produces a corrected 1600 px JPEG — detection, homography,
  per-channel flat-fielding (which is what removes the yellow cast of an indoor lamp) and the colour /
  grey-and-white finish all run in the browser, so the Worker only ever verifies and stores.
- The file is served with `cache-control: private, max-age=31536000, immutable` and an `etag` taken from
  the random key suffix: a re-scan changes both, so the editor always shows the current page. Images keep
  the `default-src 'none'; sandbox` CSP; a PDF is served `inline` without it so the browser's own viewer
  can render it.
- Deleting a scan removes the row **and** the object; the record itself is untouched.

### Workflow

`quotations.status` is `issued` or `completed`; "signed" is not stored at all — it is derived from the
presence of a scan row, so the two can never disagree. A completed record refuses `PATCH` and `DELETE`
(`409 quotation_completed`) and must be reopened first. Completing requires a signed copy
(`409 scan_required`): the stamp on the record claims the paperwork is filed, so there has to be paperwork.

### Agreements (sale and purchase)

A vehicle sale or purchase agreement is a second document kind with its own table (`agreements`), its own
templates (`templates.kind` = `sale` | `purchase`) and its own ledger. The two books never mix numbers:

- **Numbering** — `SA-<year>-<5 digits>` for sale, `PA-<year>-<5 digits>` for purchase, allocated
  atomically per company, kind and year through `agreement_sequences`. `GET …/next-number` is a preview and
  never advances the counter; `POST /api/agreements` always allocates server-side.
- **Required text** — `vehicle_model`, `vehicle_year`, `vehicle_chassis`, `seller_name`, `buyer_name`
  (`400 agreement_fields_required`, with the offending `fields` listed). Everything else may stay blank and
  prints empty, so a half-known deal can still be recorded.
- **Ceilings** — `vehicle_*` ≤ 120/20/120/40/40/40/80, `seller_*` and `buyer_*` ≤ 120/60/40/200,
  `intermediary_*` ≤ 120/40/120, `notes` ≤ 600 (newlines and repeated spaces collapse to one line).
- **Money** — `full_amount` and `paid_amount` are 0–99,999,999.99; `paid_amount` may not exceed
  `full_amount` (`400 paid_amount_exceeds_full`) because the sheet prints the balance. Both are stored in
  cents with the amount in words generated by the Worker and regenerated on every `PATCH`.
- **Status** — `issued` or `completed`, exactly like quotations: "signed" is derived from the presence of a
  scan row (`has_scan`), completing requires one (`409 scan_required`) and a completed agreement refuses
  `PATCH` and `DELETE` (`409 agreement_completed`) until it is reopened. Reopening writes
  `agreement.reopened`, closing writes `agreement.completed`.
- **Print** — `/api/agreements/:id/print` renders the `template_html_snapshot` taken at issue time against
  the agreement's own placeholders (see
  [`template-placeholders.md`](template-placeholders.md#agreement-placeholders)); `?print=1` appends the
  same hashed autoprint script as the quotation sheet.
- **Ledger and pages** — the desk's *Agreements* module lists one book per kind with search, a
  **Cancelled** view (`view=deleted`), and counts per kind (`counts`); the wizard issues a record and
  `/agreement?id=…` is its record page (`/agreement`), which also carries the signed copy, the send tools and
  the audit trail for that record.
- **Exports** — `GET /api/export/agreements.csv?company_id=&kind=` writes both books into one sheet when
  `kind=all`, with the balance as its own column.

Audit actions written by this module: `agreement.created`, `agreement.updated`, `agreement.completed`,
`agreement.reopened`, `agreement.cancelled`, `agreement.restored`, `agreement.permanently_deleted`,
`agreement.scan_uploaded`, `agreement.scan_removed`, `agreement.share_link_created`,
`agreement.share_link_rotated`, `agreement.share_link_revoked`.


`settings` is the same key/value table that holds `auth_passcode`. `quotation_share_mode` accepts `file`
(attach the signed page through the OS share sheet) or `link` (send the `/s/<token>` page); the record
page uses it as the default for each send and lets the operator override it there.

### Example session

```bash
BASE=https://desk.luxoritpro.com
curl -s -c jar.txt -X POST "$BASE/api/setup" \
  -H 'content-type: application/json' -d '{"passcode":"team-passcode","name":"Ahmed"}'

curl -s -b jar.txt "$BASE/api/companies"
CID=$(curl -s -b jar.txt "$BASE/api/companies" | python3 -c 'import json,sys;print(json.load(sys.stdin)["companies"][0]["id"])')

curl -s -b jar.txt "$BASE/api/quotations/next-number?company_id=$CID&date=2026-11-05"

curl -s -b jar.txt -X POST "$BASE/api/quotations" -H 'content-type: application/json' \
  -d "{\"company_id\":\"$CID\",\"model\":\"AUDI A8\",\"year\":\"2012\",\"chassis\":\"WAUZZZ4H0DN000001\",\"amount\":15000,\"quote_date\":\"2026-11-05\"}"

curl -s -b jar.txt "$BASE/api/quotations/<id>/print?print=1" > sheet.html
```

## Status codes used

| Code | Meaning |
|---|---|
| `400` | Validation failure (`invalid_amount`, `invalid_quote_date`, `passcode_too_short`, …) |
| `401` | Missing/expired session, or wrong passcode |
| `404` | Unknown route or unknown record (`quotation_not_found`, …) |
| `409` | Conflict (`already_configured`, `company_slug_already_exists`, `quotation_number_already_exists`) |
| `413` | Template larger than 200,000 characters |
| `429` | Login throttled |
| `500` | Unhandled error — the Worker logs `request_failed` with path, method, message, stack head |
| `503` | `/api/health` database probe failed |
